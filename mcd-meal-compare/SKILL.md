# 固定搭配比价

MCP 能查单店价格，**但查不出「同一家、同一套、哪家最省」**。那个结论必须靠编排多个接口算出来。这是本技能存在的唯一理由。

## 何时用

- 「附近哪家便宜」「比价」「哪家性价比高」
- 「我常吃的那套在别家多少钱」
- 明确要跨门店对比同一组合
- 问「配送费」

**不适用**：单店内换搭配、比套餐内小食（那是 `calculate-price` 一次调用的事）。**打包费/餐具费不查**——已从本技能移除，因为 `calculate-price` 的实测路径不稳定。

---

## 铁律：三条不许绕过

### 1. 31 位 ID 一律不许人工转录

`addressId` / `storeCode` / `beCode` / `couponId` 都是长数字串。**人工转录必然出错。**

**正确做法**：`delivery-query-addresses` 返回什么就用什么的**原样字符串**，不要重打、不要补零、不要「整理格式」。本技能编写过程中，人工转录同一个地址 ID 出错 5 次，全部返回「配送地址不存在」。

如果接口报错，**重新调 `delivery-query-addresses` 拿一次**，不要在原值上猜改。

### 2. 卡包券 ≠ 门店可用券

- `query-my-coupons` = 我**拥有**什么（资产视角）
- `query-store-coupons` = 这家店**能让我用**什么（落地视角）

比价时**必须用后者**。前者返回 `[]` 时不要报「你没券」，要报「这些门店当前无可用券」。

### 3. 夜间不硬跑

门店营业时间通常 07:00–23:00。非营业时段调 `query-meals` 会返回 `600057 门店可能已关闭或不在营业时间`。

**先判断时间**：非营业时段直接告诉用户「现在查不到，X 点开门」，**不要连续重试**。

## 执行流程

### Step 1 · 定位门店

用户给了配送地址就用 `delivery-query-stores`（需先 `delivery-query-addresses` 拿 addressId）。只给了位置关键词就用 `query-nearby-stores`（searchType=2）。

两种场景拿到的是**不同类型门店**：配送门店能外送，到店门店不能。别混用、别混着报。

门店多于 3 家时，取最近 3 家比价。全查会耗时长且用户用不上。

### Step 2 · 锁定搭配

从对话历史里提取用户的固定搭配。**常见形态**：

```
麦香鱼 + 板烧 + 小食 + 雪碧
```

用户没明确说的部分，**问一次，不要默认**。特别是：小食具体是什么（麦辣鸡腿堡/鸡块/薯条各不相同）、要不要可乐换雪碧、要不要餐具。

搭配一旦锁定，**存进记忆文件**。以后用户直接说「我那套」，不用重新问。

### Step 3 · 三层校验

对每家门店依次执行：

| 层 | 接口 | 拿到什么 | 注意 |
|---|---|---|---|
| L1 单价 | `query-meals` | 菜单里各单品现价、划线价、`discountType` | 门店间同品名可能不同价 |
| L2 可用券 | `query-store-coupons` | 该店可用的券 + 适用商品编码 | **空数组是合法结果** |
| L3 到手价 | `calculate-price` | 实付总额 | 见下方必读 |

**L3 前置条件（漏了必报错）**：
- 传了 `couponId` → **必须先调 `query-meal-detail`**，否则特制项报错
- 到店自提（beType=1）→ **不传 `beCode`**，传了报错
- 得来速（beType=5）/ 外送（beType=2）→ **必须传 `beCode`**
- `beType` 和 `orderType` 是两个东西，别混

**返回金额单位是分**，除以 100 才是元。

---

## 配送费：不要尝试

MCP 35 个工具里**没有配送费字段**。`calculate-price` 返回的是商品总额，不含运费。

遇到配送费问题，直接说「查不到，App 里能看到」，**不要用距离估算、不要编**。距离数据可以用来排序，但绝不能当运费。

---

## 输出格式

必须给出**结论**，不是表格堆砌：

```
最省：麦当劳XX店，¥XX.X
比最贵那家省 ¥XX.X

对比明细
| 门店 | 距离 | 麦香鱼 | 板烧 | 小食 | 雪碧 | 原价合计 | 可用券 | 到手价 |
|---|---|---|---|---|---|---|---|---|
| A | 3.1km | ¥20 | ¥22 | ¥8 | ¥9 | ¥59 | 满30减5 | ¥54 |
| B | 3.3km | ¥22 | ¥24 | ¥8 | ¥9 | ¥63 | 无 | ¥63 |

其他信息
· 配送费：MCP 不提供，需在 App 查看
· 券说明：B 店卡包券不可用，已用 query-store-coupons 确认
```

要点：
- **第一行就是答案**。用户要的是「去哪吃」。
- **差额要具体到钱**。「B 更便宜」没用，「B 省 ¥9」才有用。
- 查不到的项目明说，**不用近似值填空**。

## 脚本

`scripts/compare.py` — 比价矩阵计算与结论生成。

```bash
python scripts/compare.py --input stores.json --combo "麦香鱼,板烧,鸡腿堡,雪碧"
```

输入 JSON 结构：

```json
{
  "stores": [
    {
      "storeCode": "1450734",
      "name": "杨浦国伟路包头路",
      "distance": 3120,
      "items": {"麦香鱼": 2000, "板烧": 2200, "鸡腿堡": 800, "雪碧": 900},
      "couponDiscount": 500,
      "couponLabel": "满30减5"
    }
  ]
}
```

脚本负责：金额单位换算（分→元）、矩阵计算、原价合计与到手价、排序、差额计算、结论生成。

**为什么用脚本**：跨门店手算金额必错，且差额容易算反。确定性计算交给代码。

---

## 边界

- 只比价，不下单。任何写操作前必须拿到用户明确确认。
- 距离来自接口时是**米**，展示统一换算为公里。
- 券的适用商品要核对 —— `query-store-coupons` 返回的 `products[].productName` 才是这张券能打的商品。
- 单次比价超过 3 家门店会显著拖慢回复，超过时只查最近 3 家并说明。

## 已知坑速查

| 现象 | 原因 |
|---|---|
| 配送地址不存在 | addressId 转录错了，重新查地址列表 |
| 门店可能已关闭 | 非营业时段，等开门 |
| 特制项报错 | 传 couponId 前没调 query-meal-detail |
| 参数报错 | 到店自提场景多传了 beCode |
| 金额差 100 倍 | 忘了分转元 |
| 券显示为空 | store-coupons 返回空数组是合法的，不代表没券 |
